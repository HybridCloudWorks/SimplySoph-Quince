The Twilio sender, Messaging Service, API key, secrets and WhatsApp sender retirement checklist is in [twilio-setup.md](twilio-setup.md#retirement); the provisioned Twilio resources are inventoried in `ops/event-resources.json`. February 1, 2027 remains a review date only.

Protect the `simplysoph.com` registration (Hostinger), existing DNS zone and nameservers (Cloudflare), existing Google project/billing, existing mail and Notion records. ## Before creating anything

1. Authenticate to the family-selected Google account, then verify the exact project and billing state. Capture a dated, private baseline of services, repositories, secrets, identities and permissions, jobs/queues, buckets/databases, DNS, mail, and Notion objects relevant to the event. Keep full exports in restricted storage outside this public repository. Do not mark the global baseline verified until this is done. A resource may instead reference a completed scoped baseline for its specific provider and resource type; a mailbox baseline does not validate Google or DNS resources.
2. Use `misxv-2027` as the event tag and `misxv-` for dedicated resource names where supported. Labels help discovery but **are not proof of ownership**. Prefer dedicated resources where practical; for shared resources record exact changes and their prior state.
3. Record every created resource/change immediately in `ops/event-resources.json`, before proceeding to the next resource. Include exact immutable/full identity, region where applicable, creation receipt reference, dependencies, ownership checks, removal/reversal steps and verification. Record partial deployments too. Never add tokens, private guest IDs, addresses, or exported data to the public inventory; use references to restricted evidence.
4. Set `baselineVerifiedAt` only after global baseline completion, or attach a per-resource `baseline` with `verifiedAt`, `scope`, `evidence` and `allowedTypes`. Each entry has `id`, `type`, `projectId`, `ownership`, `resource`, `creationEvidence`, `verifyBeforeCleanup`, `cleanupSteps`, `verifyAfterCleanup`, `dependsOn`, and `status`. Scoped changes also require `exactScope`; DNS requires `dnsName`. See validator for supported types. Extend the inventory/plan tests before adding a new kind of resource. Project deletion and domain-registration deletion are deliberately unsupported.
5. Provisioning is incomplete until its cleanup entry exists. Do not rely on Cloud Run service deletion to remove images, secrets, logs, or other independently billed resources. Reconcile the inventory after each deployment.

## Run the workflow at the end

1. **Close intake and stop outgoing work.** Close RSVP/photo submissions, turn off event reminders, stop new queue items, drain or cancel pending work, and confirm no in-flight writes or messages remain. Remove only event schedules/triggers. Keep the site available long enough to show the agreed closing message.
2. **Choose and verify exports.** Export wanted guest/RSVP information, seating, approved photos (an administrator can use [Download all photos](#download-all-photos); unapproved media and older object generations are not in it), and any necessary correspondence to a family-controlled private destination. Test opening the export. Decide what to keep in Notion versus delete and record an export deletion date. Never put exports in GitHub or workflow logs.
3. **Generate the review.** Run `npm run cleanup:plan`, then open `work/cleanup/plan.md`. Alternatively use GitHub → Actions → **Prepare event cleanup review** → Run workflow; read its job summary. The workflow has read-only repository access, no cloud credentials, no deletion capability, and no schedule. It lists dependents before their dependencies and fingerprints the inventory being reviewed.
4. **Reconcile against live systems.** Authenticate as the intended account; inspect each exact resource and compare its creation evidence to the baseline. Check for resources created after the inventory snapshot. If a resource is shared, changed owners, or differs from the record, stop that item's deletion and resolve ownership. Review the final checklist with the family; choose the retention disposition before deleting data.
5. **Perform the recorded removal steps.** Use the provider's current console/CLI against exact IDs, checking command help before each new command. The report is a checklist, not an executable script. Remove dependencies only after their users are stopped. Mark an entry `removed` only after verification, with `removalEvidence` (timestamp and restricted receipt reference). Preserve failure records and resume only incomplete entries.
6. **Verify shutdown and remaining costs.** Regenerate the report; active entries should be empty or explicitly retained. Verify the hostname no longer routes to a removed endpoint, event endpoints are unavailable, credentials are revoked, jobs cannot send, and event resources are absent. Review billing after usage reporting catches up and again on the next statement. Existing domain/Workspace subscriptions and retained storage may continue charging.

## Download all photos

Before any cleanup, guests can keep their own copy: **Download all photos** on the gallery (`/gallery/`, `/es/gallery/`) saves every approved photo and video in one action, as ZIP files the phone's own downloader handles (Safari on iPhone saves to Files, Chrome on Android to Downloads; still to be confirmed on real phones, see the acceptance gate in [deployment.md](deployment.md)). No download deadline is shown until the family sets the site and photo lifespan (Admin → Website & event, see [publishing.md](publishing.md#site-and-photo-lifespan)); the photos date can't be earlier than the February 1, 2027 review date below. Once set, the gallery, the thank-you page and the Privacy policy's line on how long we keep information all give that one pair of dates, read from the same setting (`site/lifespan.mjs`); this runbook names no date of its own, so the date the family set in Admin is the one to work to. Setting it deletes nothing: keep **Download all photos** available through the photos date, before step 1 of the workflow above, and the site up through the site's date.

- **Who.** Guests signed in with their email (the same people who can view the gallery) and administrators. Invitation links (RSVP only) cannot. Only approved photos and videos with a stored file are included; nothing pending, rejected or still converting, and no captions or names. Files inside are named by the server: `sophia-xv-<album>-<NNN>.jpg` or `.mp4`.
- **Size limits.** One ZIP of at most 100 MB; a larger gallery comes as numbered parts ("Part 1 of 3 · 112 photos · about 98 MB"), and a single file over the cap gets a part of its own. Each part is one request through Firebase Hosting, which ends requests at 60 seconds, so a full part needs about 14 Mbit/s; the page says "Large files: on a phone, use Wi-Fi." The size is `GALLERY_ARCHIVE_PART_MB` ([deployment.md](deployment.md)).
- **Limits.** One part at a time per person, and 20 parts an hour per person. Media approved later goes into the last part, so parts already saved stay whole; if a part changed since the page listed it, the page says so and shows the new list instead of downloading a different file.
- **Owner decision, default "Signed-in guests".** Bulk saving makes it easy to keep a copy of every approved photo, including other families' children, which viewing one at a time does not. The review asked for guests to have it, so that is the default. The owner can change it in Admin → Website & event → **Download all photos**: **Only administrators** hides the action from guests and the API refuses them (`DOWNLOAD_RESTRICTED`); guests can still view and save photos one at a time.

## Resource-specific removal rules

| Resource | Cleanup boundary |
|---|---|
| Website DNS | Remove only `misxv.simplysoph.com` records and owned verification records beneath that hostname, matching the recorded type/value. Do this before deleting the destination to avoid a dangling record. Preserve root DNS, mail records, nameservers and registration. Root-domain mail verification changes need a separate reviewed reversal plan because other mail may depend on them. |
| Firebase Hosting | Remove the two recorded event DNS records first, then the event custom-domain association. Disable target `misxv` for reversible shutdown, or delete only site `misxv-simplysoph` after final review. Permanent site deletion removes releases and prevents reuse of that site ID. Preserve default site `simplysoph-66c78`. |
| Cloud Run | Remove only the dedicated event service/domain mapping after closing intake and handling DNS. Record region. Service deletion is not a full project teardown. |
| Builds and images | Remove dedicated event Artifact Registry repositories/images, temporary source archives and event build triggers. Never delete a shared repository wholesale. Record managed ancillary resources discovered during deployment too. |
| Secrets and OAuth | Revoke the event's provider tokens/grants before destroying stored secrets; remove exact event secrets/versions. Secret deletion alone does not revoke an externally issued token. Keep credentials available until their required revocations complete. |
| IAM/service identities | Remove exact event-added role bindings before deleting dedicated accounts. Reverse only the event grant, preserving other principals/roles. Remove event GitHub deployment access and identity-provider bindings. Do not disable shared APIs. |
| Storage/Firestore | Export as agreed, then remove exact event objects/collections or a verified exclusive event bucket/database. Respect retention locks and soft-delete policies; confirm deferred deletion and charges. Never delete a shared/default database wholesale. |
| Notion | Preserve the existing database and pre-existing records. Remove only approved event-created rows/properties by private ID list, or retain them as the family chooses. Disconnect/revoke only the dedicated event integration. Notion trash/backups may retain data under its policies. |
| Gmail/Workspace | Revoke only app-specific OAuth access; remove event aliases or a dedicated mailbox only after reviewing stored mail and license implications. Preserve existing mailboxes/subscriptions. Sending mail cannot be undone; copies already received by guests remain. |
| Microsoft 365 (selected mail host) | Export wanted event mail, remove the exact event Exchange app-role assignment and dedicated Entra app/credentials, then the event mailbox or alias if approved. Preserve the tenant, subscription, existing licensed mailboxes and Microsoft MX/SPF/DKIM/DMARC records. Track tenant/object IDs in lifecycle evidence; projectId denotes the associated website project, not Microsoft resource ownership. |
| Logs and budget alerts | Set appropriate log retention up front; preserve shared logs and sinks. Remove event-only alert/sink configuration after final cost review. Provider audit/billing records may remain under provider retention policies. |
| Repository/local files | After the review, clean the repository of the family's content and data and turn it into a reusable template (owner decision 18 in [v1/access-model.md](v1/access-model.md)); history keeps the old content, so publish the template from a fresh repository if that matters. Separately archive or delete ZIPs, local previews, exports and backups if requested. Remove deployed access first. Confirm the exact local path before deletion; do not delete the parent workspace or original invitation. |
